# СетьРезерв — план редизайна и живой симуляции

Статус: план, 7 ноября 2026 года. Код приложения в этом документе не менялся.

## Что есть сейчас

- React 19 + TypeScript + Vite; React Router с HashRouter, Zustand/localStorage, React Flow, Recharts, SCSS Modules, Lucide. `package.json` задаёт прямые зависимости, `package-lock.json` фиксирует их точные версии и транзитивные пакеты, а код продукта расположен в `src/`.
- Проекты: создание по трём шаблонам, поиск, избранное, архив, переименование и локальное сохранение. Проект включает схему и сценарии.
- Редактор: добавление, соединение, перемещение и удаление узлов; параметры источников, шлюза, канала и сервера; миникарта и выбор сценария.
- Сценарии: обрыв канала/сервера, рост нагрузки, время и длительность событий, режим отправки, сравнение трёх буферов.
- Расчёт `queue-1.0` в Web Worker: FIFO-очередь, потери при переполнении, доставка, задержка, p95, остатки и очистка. Запуски сохраняют снимок параметров; отчёт печатается через браузер.
- Воспроизведение уже имеет этапы, подсветку линий, паузу и скорость ×2. Навигация через `/#/editor` переживает обновление страницы.
- 28 модульных тестов прошли 7 ноября 2026 года. Кодовый аудит и текущие экраны просмотрены. Изменений в приложении в рамках этого плана нет.

## Главный разрыв между интерфейсом и ожиданием

1. Воспроизведение показывает ход событий, но не проигрывает рассчитанное состояние очереди и метрик во времени: `playback.ts` строит отдельное ускоренное расписание по границам событий, а `NetworkPreview.tsx` меняет подсветку узлов. Числа расчёта появляются уже на странице результатов.
2. Диалог воспроизведения занимает часть экрана. Для большой схемы и синхронных графиков нужен отдельный полноэкранный режим.
3. Результаты информативны, но сначала открывается плотная таблица; практический ответ и причина должны читаться до подробностей.
4. Визуальная система почти целиком держится на Segoe UI, небольших надписях, светлых карточках и одном бирюзовом акценте. У страниц мало различимого характера и визуальной иерархии.
5. Шаблон резервного пути виден на схеме, но `simulation.ts` при включённом резерве отклоняет расчёт. В новой подаче это нельзя выдавать за смоделированное переключение.
6. Старые запуски без расчёта ещё показываются через фиксированные `demoResults`. Их нужно сохранить как архивную совместимость и ясно отделить от новых расчётов без громкого слова «демо» в обычном интерфейсе.

## Решение по экранам

| Экран | Что переделать | Что пользователь увидит |
|---|---|---|
| Проекты / главная | Объединить концепты 01 и 02: выразительный верх с объёмной сетью, ниже последний проект, недавний результат и следующий осмысленный шаг. Убрать длинную постоянную инструкцию из правой колонки. | За несколько секунд понятно, зачем продукт и куда нажать. |
| Карточка проекта | Более крупная миниатюра реальной схемы, статус последнего расчёта, число источников и сценариев, явные действия «Открыть» и «Запустить». | Проекты различимы, их состояние видно до входа. |
| Редактор | Увеличить холст, сделать палитру устройств компактной, панель параметров контекстной, показать на узлах поток, предел и состояние. Добавить проверку топологии до запуска и подсветку проблемного места. | Параметры и схема читаются как единая система. |
| Параметры | Разбить длинную форму на источники, обработку и связь. Рядом с полями показывать производные значения: входящий поток, минимальная скорость цепочки, прогноз насыщения. | Понятно, как изменение числа датчиков или буфера влияет на сеть. |
| Сценарии | Визуальная шкала событий с перетаскиванием и точными числовыми полями; карточки «обрыв 60 с», «синхронный всплеск», «отказ сервера». Пересечения событий отмечать отдельно. | Сценарий выглядит как история, а не набор полей. |
| Воспроизведение | Отдельный экран: схема + временная шкала + очередь и доставка + журнал событий. Play/pause, перемотка, ×1/×2/×4, переход к ключевым моментам. | Отказ, накопление и разгрузка видны по секундам. |
| Результаты | Сверху вывод и четыре ключевых показателя, ниже синхронный график и сравнение буферов, затем полная таблица и допущения. Выделять вариант, удовлетворяющий критериям. | Видно, какой вариант лучше и какой ценой. |
| Отчёты | Собрать историю «условия → событие → поведение → вывод», добавить компактную схему, исходные параметры, версию модели и красивую печатную страницу. | Документ можно показать на созвоне без устных пояснений интерфейса. |
| Профиль | Упростить визуально; оставить настройки локального хранения и уведомлений, убрать лишний акцент с этого экрана. | Профиль не отвлекает от исследования сети. |
| Режим показа и помощник | Отдельный презентационный экран с крупной схемой и остановками на событиях. Помощник сначала отвечает заранее подготовленными фразами, подставляя только фактические показатели текущего расчёта. | Можно провести понятную демонстрацию и задавать типовые вопросы по результату. |

## Визуальное направление

Светлая тёплая оболочка, контрастный тёмный холст схемы, ясные цвета состояний: бирюзовый — поток, янтарный — нагрузка, коралловый — отказ, зелёный — восстановление. Заголовки и ключевые цифры заметнее, служебные подписи крупнее. Плавные переходы служат объяснению: импульс идёт по линии, очередь заполняется, отказ разрывает маршрут, восстановление постепенно освобождает буфер. Движение можно отключить через `prefers-reduced-motion`.

Объёмная сеть на главной — декоративный слой и вход в продукт. Для инженерного редактора оставляем точный 2D-граф. Сначала реализовать лёгкий CSS/SVG-прототип; Three.js подключать только после визуального и производительного сравнения на обычном ноутбуке и телефоне. Статичные PNG в `docs/ui-concepts-v2/` — ориентиры, не источник расчётных данных.

## Большой расчётный пример

Встроить отдельный пример «Насосная станция Северная» как **вымышленную, но параметрически согласованную** сеть. Не представлять её как сеть реального заказчика без предоставленного обезличенного кейса.

Публичный ориентир для предметной области — [пример насосной станции AWS](https://aws.amazon.com/blogs/iot/strengthening-operational-insights-for-industrial-assets-with-aws-iot-aiml-solution-part-1/): два центробежных насоса, по 30 потоков измерений на каждом, обновление 1 Гц. Это воспроизводимый учебный симулятор AWS, а не опубликованная схема заказчика. Наша схема ниже — расширенный собственный нагрузочный пример; её 700 датчиков, скорости узлов и буферы являются явными допущениями и не приписываются AWS.

Схема: восемь групп источников в четырёх производственных зонах → один шлюз → один канал → сервер. Итого 11 расчётных узлов, 10 связей; такая топология укладывается в текущую модель. Зоны служат визуальной группировкой, не создают скрытых маршрутов.

| Источник | Групп | В каждой группе | Интервал | Поток вместе |
|---|---:|---:|---:|---:|
| Температура двигателей | 4 | 100 датчиков | 10 с | 40 сообщ./с |
| Вибрация насосов | 2 | 50 датчиков | 2 с | 50 сообщ./с |
| Давление трубопроводов | 2 | 100 датчиков | 5 с | 40 сообщ./с |
| **Итого** | **8** | **700 датчиков** |  | **130 сообщ./с** |

Шлюз: 180 сообщ./с, буфер 8 000 сообщений. Канал: 160 сообщ./с, задержка 20 мс. Сервер: 220 сообщ./с. Узкое место — канал 160 сообщ./с. Сценарий: 10 минут наблюдения, обрыв канала с 04:00 на 60 секунд. Для сравнения: буферы 4 000, 8 000 и 12 000. До запуска показать расчётный входной поток 130 сообщ./с и объём поступления за минуту отказа около 7 800 сообщений; **потери, точный пик и время очистки брать только из движка**, а не из приближённой формулы.

В интерфейсе пользователь открывает этот пример одним нажатием, видит зонированную схему и редактирует исходные числа. При запуске потоки и очередь показываются на ней же; изменение количества, интервала, скорости канала или буфера меняет результат следующего запуска. Для первого релиза не добавлять второй активный шлюз или резервный канал в расчётный пример: текущая модель этого не поддерживает.

## Как сделать симуляцию «живой» без подмены расчёта

1. Расчёт по-прежнему выполняется полностью в Web Worker. Он возвращает снимок запуска и временные данные: точки очереди, доставки, потерь, статусы узлов, границы событий. Интерфейс не выдумывает числа во время анимации.
2. Воспроизведение читает этот снимок по общему курсору времени. Схема, график, счётчики и журнал событий получают состояние от одного времени. Перемотка назад восстанавливает то же состояние без нового расчёта.
3. В начале показать базовый поток; на отказе разорвать линию и подчеркнуть накопление в шлюзе; после восстановления ускорить поток и показать уменьшение очереди. В конце переход к сравнению размеров буфера.
4. Потоковые частицы обозначают направление и интенсивность, а не одно визуальное движение на каждое из сотен тысяч сообщений. Крупные значения и график всегда соответствуют расчётной трассе.
5. Для хорошего понимания — короткие текстовые пояснения именно в моменты изменения: «канал остановлен», «очередь достигла 50%», «сообщения вновь доставляются», «буфер освободился».
6. Проверить производительность на больших схемах: ограничить число анимированных элементов, использовать Canvas/SVG по нагрузке, останавливать анимацию в скрытой вкладке, учитывать reduced motion.

## Порядок реализации и код

1. **Основа оформления.** Токены, типографика, сетка, цвета состояний, компоненты и адаптивность: `src/styles/global.scss`, `src/styles/App.module.scss`, `src/components/ui.tsx`. Два варианта главной свести к одному выбранному направлению.
2. **Главная и большой пример.** Переделать `Projects.tsx`, добавить отдельную фабрику примера в `src/data/`, миниатюры в `NetworkPreview.tsx`; не ломать уже сохранённые проекты.
3. **Редактор и сценарии.** `Editor.tsx`, `Scenarios.tsx`: новый холст, инспектор, проверка допустимости схемы, наглядная шкала и понятные настройки. Существующая числовая валидация остаётся основанием для расчёта.
4. **Трасса и экран воспроизведения.** Расширить `simulation.ts` и тип `Calculation`, затем переписать связку `playback.ts` / `ScenarioPlayback.tsx` / `NetworkPreview.tsx` вокруг общего курсора. Старые снимки распознавать по версии; при отсутствии трассы показывать доступный им прежний режим.
5. **Результаты и отчёт.** `CalculationView.tsx`, `Results.tsx`, `Reports.tsx`: вывод, сравнение и печатное оформление. Старые фиксированные результаты оставить только для совместимости с архивом; обычный новый путь — исключительно рассчитанный.
6. **Дополнительный слой.** Режим презентации и ограниченный помощник с готовыми, проверяемыми ответами на фактах текущего расчёта. Без backend и без заявления о полноценном ИИ.
7. **Отдельный будущий этап.** Несколько активных шлюзов, резервирование и переключение маршрутов потребуют новой модели очередей/маршрутизации, её тестов и отдельной проверки. Не маскировать это одной анимацией.

## Критерии готовности

- Пользователь без подсказки проходит путь: открыть пример → изменить параметры → настроить обрыв → посмотреть ход → сравнить буферы → открыть отчёт.
- Значение очереди и статусы во время воспроизведения совпадают с рассчитанной трассой на выбранном времени; пауза, перемотка и повторный запуск дают одинаковые значения.
- Большой пример действительно пересчитывается при изменении параметров и не содержит неподдерживаемых активных ветвлений.
- Старые проекты/запуски после обновления открываются; снимки прошлых расчётов неизменны.
- Проверены обновление маршрутов, desktop/mobile, клавиатура, контраст, reduced motion, печать и автоматические тесты расчёта.
- Границы модели и происхождение исходных данных доступны в деталях результата, без навязчивого слова «демо» на основных экранах.
